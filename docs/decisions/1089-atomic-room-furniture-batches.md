# 1089 — Accept a room's pending furniture and projects atomically

Date: 2026-10-03

Status: Core paired-allocation increment independently reviewed and verified; spatial coordinator and live UI composition remain in progress.

## Purpose

Decision1087 admits the entire RoomLayout operation before any copied geometry and
requires all escaped views to end within the same input call. A confirmed layout
must next publish actual pending Furniture and Construction identities together.
It cannot call immediate surface furnishing or allocate a prefix then roll back
Directory generations after a later refusal.

This packet preserves the approved completed-empty-shell furnishing gate and
permanent Room type. Each item gets its own real Furniture and Construction refs;
acceptance grants no installed service. Later delivery, real Jobs/Gear/Work,
shared receipts, installation and cancellation keep using the actual existing
ModularProjects/FurnitureWork/RoomOrders owners. There is no master Project,
caller recipe, duplicate payment arena, new identity kind or surrogate surface
Building. UI confirmation is group-atomic, not instant construction.

## One exact observed identity transaction

For N entries, RoomOrders creates one Directory.CreateBatch containing exactly
2N alternating Furniture and Construction observations. It does so only inside
the actual Layout Sources cold token, after the owner has admitted all copies,
companions, source checks and native growth. It separately pins all five tuple
columns and the exact copied player entries before exposing any mutable packet
to a provider. Capacity and generation exhaustion refuse before payment or
identity allocation; all original Directory state bytes remain unchanged.

Buildings preflight verifies the actual completed underground Room binding,
known floor-furniture type/rotation, free actual Furniture typed rows and exact
bound RoomOrders candidate attestation. Construction preflight verifies the
paired actual Construction rows and its protected furniture recipe/work tables.
No caller supplies a work amount, material quantity or worker limit. A single
existing component Quote can be reused; there are no N Quote instances.

The actual Router owns the exclusive final acceptance bracket. It establishes
its busy/prepared state before any purpose-owner/provider callback, checks the
exact bound FurnitureWork purpose owner, and obtains final non-mutating current
source, cold-token, identity, catalog and capacity proof. It then performs:

1. One `Directory.create_batch` with the exact still-current observed choices.
2. Callback-free initialization of actual pending Buildings Furniture rows and
   actual protected-catalog Construction rows, including all reuse resets.
3. The already prepared, non-failing source/geometry/companion publication in the
   exact same-stack Furniture batch window.

All fallible allocation, geometry and public proof callbacks finish before the
first Directory write. The output's2N project slot/generation integers are
preallocated before this boundary, inside the1087 receipt allowance. A successful
command returns those actual project refs in input order. Failure before identity
publication leaves all authoritative owners unchanged. Post-publication cleanup
cannot be mislabeled as an atomic command refusal, following1087's correction.

profiles, full room compatibility, old/new contacts and protected circulation

## Cold storage accounting

No authoritative owner columns are added. With N entries, the reviewed packet
plan is:

| Simultaneous payload | Logical bytes |
| --- | ---: |
| Directory observation including frontier/kind scratch (K=2N) | 48N+76 |
| RoomOrders private five-column identity pins | 40N |
| RoomOrders submitted and canonical entry copies | 32N |
| Geometry bridge's tuple, entry and source-row pins | 60N |

The8N-byte kind request is dropped before the40N tuple pins are created; it is
not an additional simultaneous peak. The8N output project receipt is already
part of1087's B1 allowance, not omitted or counted as a second owner arena.
Fixed scalar controls, object/Variant/container headers, provider geometry images,
companions and allocation growth must be added under the same exact token before
any copy. The source records will pin those controls as implementation settles.
This arithmetic is not an independent-max production admission or measured RAM
qualification. No per-resident/per-tick batch allocation is permitted.

The first core increment adds no packed columns. The actual Router borrows one
CreateBatch reference and retains a Vector2i batch Room plus a publication bool:
**9 logical numeric bytes**. Two helper-frame scalars pin accepted count and the
first full Project ref before any publication callback: **16 logical bytes**
during publication, in addition to native references/headers and the ordinary
one-command OpResult. These are transient admission controls, never saved or
hashed; the legal quiescent boundary has no borrowed candidate or publication

Independent review found a receipt-lifetime defect in the initial Router draft:
the final companion callback could legitimately clear borrowed packet scratch
before the Router read its success count/ref. The corrected implementation pins
both scalars immediately after Directory success and before any publication
callback. A regression deliberately clears both packet and entries after seeing
the actual rows; the caller still receives the truthful committed count and full
Project ref, and repeating the cleared packet cannot allocate again. Cleanup
never turns a committed command into an ordinary refusal.

The independent root agent rechecked the final pinned source and adversarial
tests after that correction, accepted it with no remaining high/medium finding,
and did not duplicate the author's runtime checks. The review is limited to this
actual core owner boundary; the synthetic geometric permit remains disclosed.
